"Found in the 1.2.1 smoke run on 2026-09-08 (station S6, High Contrast block). Two surfaces the forced-colors pass in [#542](https://github.com/Stashpeak/SimLauncher/issues/542) never listed, so nothing restores them. **Neither is a regression**; both have been in this state since the block was written.

Four things were observed in a Contrast theme. Two of them turned out to be the mode working correctly and are deliberately **not** part of this issue, recorded at the bottom so nobody re-files them.

## 1. The accent swatches lose the only information they carry

Settings > Appearance renders seven preset swatches plus the custom one as **empty outlined circles**. The whole job of that control is to show which colour it applies, so this is not \"different in High Contrast\", it is a control that no longer works.

Every swatch paints its colour with a background: the presets use `bg-(--preset-color)` with the hex injected inline (`AccentSwatchRow.tsx:50-57`), and the custom swatch's colour layer uses either a `background-color` or a `conic-gradient` (`AccentSwatchRow.tsx:81-89`). forced-colors replaces `background-color` with a system colour and forces a non-`url()` `background-image` to `none`, which is exactly what the mode is for.

**`forced-color-adjust` does not appear anywhere in this repo** (grep over all tracked files: zero matches), and nothing in the forced-colors block (`App.css:913-982`) matches either swatch button. This is the one place in the app where the colour **is** the content, which is precisely the case `forced-color-adjust: none` exists for.

The residual cues do not substitute. `aria-pressed` and `aria-label` (`AccentSwatchRow.tsx:53-54`) serve a screen reader, and the tooltip opens on hover and on keyboard focus, so a sighted user can read one name at a time serially. That makes the control **operable, not readable**. Compare `ColorPickerPopover.tsx:152-176`, which keeps a HEX text field and therefore has a genuine non-colour path to the same information; the preset row has none.

Three things have to change together, or restoring the fill makes it worse:

- `forced-color-adjust: none` on the preset button (`AccentSwatchRow.tsx:50`) and on the custom swatch's enclosing button (`:76`), which covers its colour layer by inheritance.
- **An explicit border on every swatch.** Today the unselected swatch has `border-transparent` (`:55`, and `:102` for the custom ring). Once the real colour is back, a swatch near the theme's `Canvas` (a black or white custom accent) is invisible. System colour keywords still resolve inside a `forced-color-adjust: none` subtree, so the ring can sit on the same element, but it has to be authored, because the UA no longer forces anything there.
- **The selected indicator has to stop being the accent.** It is `border-(--accent)` (`:55`, `:102`). Under `forced-color-adjust: none` that resolves to the live accent, and the commonest case is the accent swatch being the selected one: an accent ring on an accent fill, invisible. It should become `Highlight`, matching the convention already set at `App.css:938-942`.

The `scale-110` on the selected swatch (`:55`, `:77`) is a real second cue and is what currently keeps the selected state legible in the screenshot from this run, so it should be kept, not relied on alone.

## 2. The open profile menu has no edge

The run sheet asserts this one directly, as a regression guard attached to #884: *\"the open profile menu has a visible border and background.\"* **It fails**, on the border half outright.

Three different elements, and only two are covered:

| Element | Class | Covered in forced-colors? |
|---|---|---|
| Trigger | `dropdown-trigger-surface` (`GameRowProfileMenu.tsx:128`) | yes, `App.css:933` |
| Checked item | `dropdown-item[aria-checked='true']` (`:186-188`) | yes, `App.css:940` |
| **The menu surface** | `dropdown-surface overlay-glass` (`:169`) | **no** |

`.dropdown-surface` (`App.css:525-528`) paints only a `linear-gradient` background, forced to `none`, and a `box-shadow` whose `inset 0 0 0 1px` hairline **is the panel's only edge** and is stripped in this mode. `.overlay-glass` adds an rgba background that resolves to `Canvas` plus a `backdrop-filter` that means nothing once the backdrop is a flat system colour. There is no `border` utility on the element.

So the menu renders as an opaque `Canvas` rectangle with no edge, on a `Canvas` page. It occludes what is behind it but nothing marks where it starts or stops.

**This is an omission, not a house style.** The repo's other floating menu, `useDismissMenu.tsx:113`, carries the identical class pair **plus** `border border-(--glass-border)`. An author border-color survives forced-colors, forced to an opaque system colour, so that menu keeps its edge in a Contrast theme and this one does not.

**Not a regression from [#940](https://github.com/Stashpeak/SimLauncher/pull/940).** `git show 6467780a~1` shows the pre-portal className had no border either; the class has been on this element since 2026-05-02. #940 changed how the menu is positioned, not whether it has an edge.

Preferred fix: add `.dropdown-surface` to the border list at `App.css:928-936`, which covers both menus and anything future. `CanvasText` reads better than `ButtonText` for a container rather than a control.

## Deliberately not filed, so they do not come back

**The status dots both render white.** Correct, and already decided. #542's scope specified `CanvasText`/`Highlight` dots, and [PR #850](https://github.com/Stashpeak/SimLauncher/pull/850) settled the WCAG 1.4.1 question in as many words: *\"Windows High Contrast collapses every dot to one system colour and the two states would otherwise be identical. Shape is what the OS could not take away.\"* The rules hold today: `.status-dot` becomes a solid `CanvasText` disc (`App.css:962-965`) and `.status-dot-unknown` overrides it to `background: Canvas` with a `2px solid CanvasText` ring (`App.css:973-976`), source order pinned by a test (`tests/renderer/gameIconDismiss.test.tsx:288-293`). Filled disc versus hollow ring, plus a distinct accessible name on each. Confirmed as a ring in the screenshot from this run.

**The Close Apps X renders white.** Also correct. It differs from Launch by glyph (`KillIcon` vs `PlayMarkIcon`) and by accessible name, and the two are mutually exclusive states of one control rather than neighbours. Substituting the danger red for the system foreground is what the mode is for. Note also that the secondary icon-action variant is `color: var(--text-muted)` at rest **in every mode** by design (`App.css:442-451`), danger only on hover, so if that was the button seen, white at rest is not a High Contrast behaviour at all.

## Dating

The forced-colors block landed 2026-06-14 (`9d0e997`, #542, milestone 1.0.0) and its scope list enumerates the focus ring, the action classes, the trigger surface, the toggle, the status dots and row opacity. It never mentions the swatch row or the menu surface. No comment anywhere records a decision to let either go.

## Priority

Population: users running a Windows Contrast theme, a small slice, but the ones for whom this is the whole experience rather than a preference. Severity: the accent picker is unusable rather than degraded, which is the higher of the two; the menu edge is a legibility loss with no functional consequence. Both fixes are small and land in the same CSS block.
